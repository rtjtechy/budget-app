§03

Multi-tenant model

"One system, every store"

You run one codebase, one Meta app, one database. Every table carries a store_id. Inbound messages are routed to the right store by the phone_number_id Meta includes in the webhook payload. Two onboarding stages, both direct with Meta:

Stage A · now

First 1–10 stores

Register each store's WhatsApp number under your own WABA. One WABA holds several numbers, each with its own phone_number_id.[1][6] You hold one permanent token; map phone_number_id → store_id in your DB. You pay Meta directly — zero BSP markup.

Stage B · scale

Many independent stores

Become a Meta Tech Provider and integrate Embedded Signup: each store clicks a button and connects their own WABA + number; your app is authorized to message on their behalf.[2][3] A Tech Provider solution can onboard ~200 clients per rolling week.[6]

CONSTRAINT
Meta does not allow senders from different businesses inside one WABA.[5] Stage A is ideal when shops operate under your CartzApp umbrella. When a store is a separate legal business wanting its own billing, use Stage B.
REALITY
Tech Provider status needs app review + business verification, which can take weeks. Start that paperwork early, in parallel with building.[1][5]
DECISION
Build the whole app on the Stage A path first (it's a strict subset of Stage B). Add Embedded Signup later without rearchitecting — your routing is already keyed on phone_number_id.

§06

The AI ordering agent

The core — LLM + tools, grounded in the database

Loop: receive customer text → give the LLM the system prompt + conversation history + available tools → the model calls tools → you execute them against the DB → feed results back → model produces the reply → you send it.

ToolPurpose
get_menu(category?)Returns only available, in-stock items + prices for this store.
add_to_cart(...)Validates availability + stock, adds line.
modify_item / remove_itemEdit cart.
view_cart()Returns lines + live total from DB.
set_fulfillment(...)Pickup or delivery.
confirm_order()Finalizes: re-checks stock, writes order, decrements inventory.
handoff_to_human(reason)Flags the conversation for the owner.
PROMPT
System prompt (per store, injected at runtime): store name + language + currency + live menu + active notices/gates + the rules — only sell items returned by get_menu; never quote a price yourself, always read it from a tool result; always read the cart back and get an explicit "yes" before confirm_order; if unsure, call handoff_to_human.

Grounding & guardrails:

  • Menu and totals come from tool results, not the model's memory → no hallucinated items/prices.
  • confirm_order re-validates stock inside a DB transaction (the cart may have been built minutes ago).
  • Cap tool-call iterations per turn (e.g. 5) to avoid loops.
  • Multilingual is automatic — the model replies in the customer's language. No translation layer.
agent_loop.pseudo
function handleMessage(store, customer, text):
    convo   = conversation.load(store, customer)
    history = convo.messages + [user(text)]
    tools   = registry.for(store)
    loop up to 5 times:
        resp = llm.create(system=systemPrompt(store, convo), messages=history, tools=tools)
        if resp.wants_tool:
            result = execute(resp.tool, store, convo)     # hits the DB
            history += [resp, toolResult(result)]
            continue
        else:
            whatsapp.sendText(store, customer, resp.text)
            conversation.save(convo)
            break
§07

Inventory management

Ship v1 first, layer the rest progressively
v1 · ship this
  • Each product has track_stock. If false, it's just an availability toggle. If true, it has stock_qty + low_stock_threshold.
  • get_menu returns an item only if is_available AND (track_stock false OR stock_qty > 0) → AI can never offer something that's out.
  • On confirm_order, in one DB transaction: re-check stock, decrement, write an inventory_movements row, and auto-86 (set is_available=false) any item that hits 0.
  • Owner dashboard: edit stock, restock (logs movement), toggle availability; low-stock highlighted; threshold alerts fire.
progressive
  • Full movement history & daily reset for freshly-prepared items.
  • Ingredient/recipe-level deduction (one sandwich = 1 bun + 50g cheese).
  • Supplier records, purchase orders, reorder suggestions.
  • Demand analytics → forecast prep quantities.
§08

Build phases

Do these in order
1

Meta Cloud API direct setup

Start today · verification is slow
  1. Create a Meta Business portfolio at business.facebook.com.
  2. Register as a Meta developer, create an App (type: Business), add the WhatsApp product.
  3. On WhatsApp → API Setup you get a free test number, a 24h token, and a phone_number_id.
  4. Add a real phone number for production and a payment method (mandatory, even for sending).
  5. Generate a permanent access token via a System User with whatsapp_business_messaging + whatsapp_business_management scopes. Production must use this.
  6. Start Business Verification now — it gates production and can take weeks.
  7. Note your WABA_ID, PHONE_NUMBER_ID, PERMANENT_TOKEN, APP_SECRET, and a self-chosen VERIFY_TOKEN.
2

Local dev + echo bot

Prove the round-trip

Scaffold the backend; expose two routes at /webhook. Verification (GET) answers Meta's challenge; receive (POST) verifies signature, ACKs 200 immediately, then enqueues.

webhook.js
// GET — Meta calls this once when you save the webhook
app.get('/webhook', (req, res) => {
  const { 'hub.mode': mode, 'hub.verify_token': token, 'hub.challenge': challenge } = req.query;
  if (mode === 'subscribe' && token === process.env.VERIFY_TOKEN) return res.status(200).send(challenge);
  return res.sendStatus(403);
});

// POST — verify signature, respond 200 immediately, then enqueue
app.post('/webhook', (req, res) => {
  if (!validSignature(req)) return res.sendStatus(401);  // X-Hub-Signature-256 vs APP_SECRET
  res.sendStatus(200);                                   // ACK fast or Meta retries
  queue.add('inbound', req.body);                        // process off-thread
});

Payload path: entry[].changes[].value.messages[], store key at value.metadata.phone_number_id, sender at value.contacts[].wa_id. Run a tunnel, set the public URL as the Callback URL, paste your VERIFY_TOKEN, subscribe to the messages field, and wire the worker to echo back. When that round-trips, your plumbing is real.

3

Data layer + tenant routing

Schema · seed · route
  1. Create the Postgres schema from §4 (migration tool: Prisma / Drizzle / Alembic).
  2. Seed one store with its phone_number_id and a small real menu (Royal Karak).
  3. In the worker: read phone_number_id → look up store_id. Load/create customer + conversation. Dedupe on wa_message_id. Refresh window_expires_at (now + 24h) on each inbound message.
4

The AI ordering agent

Replace the echo worker
  1. Add the LLM client and implement the §6 tools against the DB.
  2. Write the per-store system prompt builder (menu, language, notices, rules).
  3. Implement the agent loop (cap iterations). Replace the echo worker with it.
  4. Test in 2–3 languages: order, change quantity, ask "what do you have," confirm. Verify prices/stock always come from the DB.
5

Orders, inventory, dashboard

The operator console
  1. Implement confirm_order: transactional write of orders + order_items, inventory decrement + movement log, state → confirmed.
  2. Build the owner dashboard (React, reuse your prototype): login, live orders feed + kitchen board (realtime), menu + inventory editor, settings/notices, analytics.
  3. Push new confirmed orders to the kitchen board in real time.
6

Outbound notifications

Templates
  1. In WhatsApp Manager, create + submit message templates for order status (order_confirmed, order_ready) and wait for approval.
  2. Notification service sends these on state changes. Inside the 24h window a reply is free; outside it you must use an approved template (the paid path) — keep these minimal.
7

Payments

Optional for v1
  1. Start with cash / pay-on-pickup.
  2. When ready: generate a payment link (Stripe / Telr / Network International), send it, update payment_status from the provider's webhook.
8

Evals & observability

Measure before you trust
  1. Collect 20–50 real order messages → a test set with expected carts. Auto-score the agent on every prompt change against your "done" bar (e.g. 9/10).
  2. Add LLM tracing (Langfuse / LangSmith): inspect every conversation, tool call, latency, and token cost per order — your real variable cost.
  3. Add app logging + error alerts; confirm idempotency and the human-fallback path work.
9

Deploy

Two processes
  1. Containerize. Deploy the web/API and the background worker. Add managed Postgres + Redis (Upstash).
  2. Put the API behind an HTTPS domain; set that as the production webhook Callback URL.
  3. Move all secrets to env vars. Re-subscribe the webhook to the production URL.
  4. Smoke-test end-to-end on the real number once business verification clears.
10

Replicate to more stores

Routing already handles it
  • Stage A (now): for each new store, register its number under your WABA, add a stores row with its phone_number_id, seed its menu. No code change.
  • Stage B (scale): integrate Embedded Signup so stores self-onboard their own WABA/number; your onboarding service captures their phone_number_id and waba_id. Same routing, same agent.

§11

Cost model

Recap
  • Per-message pricing since 1 July 2025; customer-initiated chats get a free 24-hour reply window, so the AI ordering conversation is free on Meta's side — you pay only LLM tokens.[4]
  • You pay Meta only for business-initiated templates (status updates, marketing), priced by category + recipient country.[4]
  • Going direct (no BSP) removes the per-message BSP markup[4] — your cost-efficiency goal. The trade-off is you build the tooling yourself, which this runbook covers.
